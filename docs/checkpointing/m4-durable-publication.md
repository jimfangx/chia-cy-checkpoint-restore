# M4 durable publication — iteration 34

M4 remains in progress. `entry.cc` still rejects production `+fs-checkpoint`
and `+fs-restore`. This increment supplies durable publication for the existing
complete aggregate and its local restore staging; it does not connect those
operations to the production runtime entry.

Both word and packed aggregate APIs now provide `publish_aggregate(...)`.
Checksum, executable/build, complete membership, per-address padding, harness
phase and bound target-cycle validation precede temporary creation. The shared
`durable.atomic_output` writes an exclusive mode-0600 file in a pinned destination
directory, flushes/fsyncs it, atomically replaces the destination, then fsyncs
the directory. Staging uses the same sequence. The production test entry's
verifier reopens the committed `.fsckpt` before preparing fresh-process staging.
Native payload semantics and all VPI owners still undergo complete compiled
prevalidation before any load/deposit; publication does not bypass that check.

Failures before rename preserve the previous destination, or its absence.
Failures after rename raise `PublicationError(published=True)`: the complete
replacement may be visible but directory durability is unconfirmed. A second
flush/cleanup failure cannot hide the original publication status. Unsupported
directory sync, symlink/special destinations and I/O failures fail explicitly.
Concurrent readers see complete old/new files; readers holding an open file
retain that inode. Concurrent publishers use distinct temporary files and the
last rename wins. A killed writer can leave a private `.pending-*` file, which
is not a committed checkpoint and is never automatically removed by another
writer. This is local publication, not rolling retention or FPGA transport.
